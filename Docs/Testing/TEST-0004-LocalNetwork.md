# TEST-0004 — 로컬 전용 서버·다중 클라이언트

## 범위

사용자는 Steam App ID·PlayFab 프로젝트를 아직 준비하지 않았으며, 먼저 같은 PC의 별도 전용 서버와 2~4개 클라이언트를 검증하기로 결정했다. 서버는 `StartServer`로 실행하며 방장 클라이언트와 별도 프로세스다. loopback 주소 `127.0.0.1`만 수신하므로 다른 PC 접속·공개 인터넷 배포 시험이 아니다. 방화벽·클라우드 계정·과금 자원·Game Ban은 변경하지 않는다.

## 구현과 재현

- 담당: [Online](../../Assets/Game/Features/Online/README.md).
- 실행: 프로젝트 루트에서 `pwsh -NoProfile -File ./LocalNetwork.ps1 -Mode Test -Players 2`, 같은 방식으로 `-Players 4`.
- 과도 요청 격리: `pwsh -NoProfile -File ./LocalNetwork.ps1 -Mode Test -Players 2 -Scenario Guard`. 렌더 검사: `-Mode Test -Players 2 -Capture`.
- 창을 직접 확인: `pwsh -NoProfile -File ./LocalNetwork.ps1 -Mode Play -Players 2`. 시험 클라이언트 두 창과 숨겨진 별도 서버가 열린다. 모든 참가자가 나가면 서버도 종료한다.
- 보고서: `Logs/Network/2-player/result.json`, `Logs/Network/4-player/result.json`과 개별 서버·클라이언트 JSON/로그.
- 재실행은 같은 결과 파일을 최신 결과로 바꾼다. 실행별 식별자를 모든 보고서와 대조하여 이전 성공 결과를 재사용하지 않는다. 실패 시 이번 스크립트가 실행한 프로세스만 정리한다.
- 자동 시험은 `-batchmode -nographics`로 별도 프로세스 통신을 검사한다. 실제 창 클릭·3D 렌더·프레임 성능 검사를 대신하지 않는다. 저장 경로도 개별 QA 경로로 분리한다.

## 현재 증거

2026-09-19 `PrototypeNetworkRoomTests` 6/6 통과, 실패 0, 0.223초. `Logs/network-room-model.xml`은 순수 서버 방 모델 검사다.

별도 프로세스 검사는 **2인·3인·4인 모두 통과**했다. 통합 Full에서 2인은 16:01:13~16:01:33(KST), 3인은 16:01:34~16:01:54, 4인은 16:01:55~16:02:18에 실행했다. 각 검사는 전용 서버 1개와 실제 정상 클라이언트 2~4개, 거부 확인용 클라이언트 2개를 별도로 시작했다. 모든 프로세스의 정상 종료 코드 0과 같은 실행 식별자를 확인했다. 서버의 권한/중복 거부는 2·3·4인에서 각각 2·4·6회이며 접속 거부는 각각 2회다. 각 클라이언트 보고서의 오류 목록은 비어 있다.

초기 검사 스크립트는 Unity JSON의 null 클래스 필드가 빈 객체로 직렬화되는 것을 연결 완료로 오인했다. 실제 접속 슬롯과 비어 있지 않은 서버 ID를 모두 기다리도록 수정한 뒤 위 결과를 얻었다. 게임 판정을 통과시키기 위해 검사 조건을 제거하지 않았다.

과도 요청 격리 검사도 **통과**했다. 최신 통합 실행 16:02:19~16:02:28(KST)에서 시험 클라이언트가 60개 요청을 연속 송신했고, 서버는 허용된 첫 30개 뒤 초과 요청을 거부해 해당 연결만 종료했다. 정상 클라이언트는 방장 역할과 동일 서버 ID·진행하는 서버 시계를 유지했고, 계정 제재나 타 프로그램 접근은 없었다. 보고서는 `Logs/Network/guards`에 있다. 고정 1초 창의 개발용 제한이며 인터넷 환경 오탐·부하·상용 안티치트 검증은 아니다.

멀티 대기실의 실제 GPU 렌더도 생성해 직접 열었다. 이 경로는 일반 게임 캡처와 같은 `PrototypeFrameCapture`를 사용한다. 첫 2인 이미지 이후 4인 명단 잘림을 예방하도록 이름/상태를 독립 4행으로 바꿨다. 보강 빌드 후 16:08:29~16:08:53(KST) 4인 통신·렌더 재검사 통과, `Logs/Network/4-player/waiting-room.png`에서 네 명의 이름·준비 상태·방장 표기와 네 캐릭터를 직접 확인했다. 이는 오프스크린 렌더이며 실제 창 마우스 조작/성능 증거가 아니다.

동일 보강 빌드로 16:11:06~16:11:27(KST) 2인 통신·렌더 재검사도 통과했다. `Logs/Network/2-player/waiting-room.png`를 직접 열어 2/2 명단·두 캐릭터·한국어 안내를 확인했다. 16:02 Full 이후의 런타임 변경은 이 대기실 행 배치 보강이며, 기존 77개 PlayMode를 다시 실행한 것으로 표시하지 않는다.

모델 검사는 2·3·4인 정원, 시작 명단 고정, 방장 이탈 후 서버·런 ID/시계 보존, 잘못된 버전·이름·순서 거부, 준비 조건 및 스냅샷 복사 독립성을 포함한다.

별도 프로세스 검사는 정상 참가자 전원이 동일 서버 ID·참가 명단·챕터를 받는지, 버전 불일치와 정원 초과 접속이 거부되는지, 일반 참가자의 챕터 변경과 중복 요청이 거부되는지, 방장 종료 뒤 서버·시계·출발 명단이 유지되는지 검사한다. 비정상 패킷 때문에 정상 참가자를 계정 제재하지 않는다.

추가 장애 검사도 통과했다. 2026-09-19 16:21:39~16:22:05(KST), `pwsh -NoProfile -File ./LocalNetwork.ps1 -Mode Test -Players 4 -CrashOwner`로 이번 검사에서 생성한 방장 클라이언트 프로세스만 강제 종료했다. 남은 3개 클라이언트와 서버에서 방장 역할 이전, 동일 서버·런 ID, 고정 출발 명단과 진행하는 서버 시계를 확인했다. 결과는 `Logs/Network/4-player-crash/result.json`이다. 강제 종료한 방장의 비정상 종료는 의도된 시험 조건이며, 챕터 플레이 중 장애 복구까지 검증한 것은 아니다.

## 검증 경계

현재 `Reserved`는 출발 명단 고정 상태다. 대기실 통신 통과는 챕터의 이동·아이템·구조·퍼즐·출구·점수가 실제 멀티플레이에서 동작한다는 증거가 아니다. Steam 인증·초대, PlayFab 배포, 재접속/안전 구간 합류, WAN 지연·손실·장애·악성 클라이언트 검증, 최저 사양 프레임은 남은 항목이다. 최종 SDK 결정과 시험 배점/콘텐츠 승인도 별개다.
