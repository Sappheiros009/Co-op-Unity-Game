# 프로젝트 작업 원칙

## 문서 기준

[Plan.md](../Plan.md)를 다른 사람이 읽는 통합 기획서로 유지한다. 확정한 내용은 질문·선택지·답변·AI 검토 대화를 제거하고 게임 규칙, 책임, 검증 기준으로 작성한다. 같은 질문을 다시 묻지 않는다.

미정인 항목은 [PROJECT_STATE.md](PROJECT_STATE.md)에 짧은 결정 과제로 남긴다. 새로운 조율이 필요하면 사이드바에서 영향이 큰 1~3개의 객관식과 직접 설명할 여지를 제공한다. 추천과 무응답을 확정으로 처리하지 않는다. 결정 후에는 다시 서술형 기획으로 반영한다.

2026-09-19 사용자 추가 원칙: 더 나은 대안이 있어도 비용·핵심 구조·범위·최종 표현 변경 등 별도 승인이 필요한 경우에는 해당 작업을 잠시 중지하고 사용자에게 승인을 요청한다. 추천안·기존안의 장단점·비용·영향과 선택지를 사이드바에 제시하고, 승인 전에는 실행·구매·확정하지 않는다. 이미 승인된 범위의 독립적인 검증은 진행할 수 있지만 보류된 결정을 우회해 구현하지 않는다.

## 사용자 경험·프론트엔드 결정권

이 프로젝트에서 프론트엔드는 플레이어가 보고·듣고·느끼는 클라이언트 경험 계층을 뜻한다. 다음 항목은 AI가 후보와 장단점을 제시할 수 있지만, 최종 결정권은 사용자에게 있다.

- 캐릭터·몬스터·보스의 외형, 실루엣, 색상, 재질, 장식
- UI/UX의 레이아웃, 색상, 폰트, 아이콘, 메뉴 스타일, 정보 표시 방식
- VFX·SFX·음악·애니메이션·카메라·조명·후처리의 연출 방향
- 지역의 시각 테마, 분위기, 사운드 테마, 사용자에게 보이는 난이도 표현

AI 추천안은 위 항목을 자동 확정하지 않는다. 사용자가 제공한 레퍼런스가 없으면 임시 플레이스홀더 또는 비교 후보로만 제시하고, 확정된 사용자 요구와 승인된 레퍼런스가 생긴 뒤 제작 지시로 승격한다. 저사양 최적화로 프론트엔드 표현을 줄여야 할 때도 변경되는 시각·청각 경험과 성능 이득을 함께 설명하고 사용자 승인을 받는다.

LOD·메모리·렌더링 비용·파일 구조·라이선스·버그 추적·네트워크 책임 같은 기술·운영 항목은 AI가 기본안을 추천하고 검증할 수 있다. 단, 기술 선택이 프론트엔드의 표현이나 플레이 경험을 바꾸면 해당 변경 부분은 사용자 결정 항목으로 되돌린다.

최신 사용자 결정, 확정 기획, 상세 설계 순으로 대조한다. 서로 충돌하면 근거를 확인하고 미결 부분을 분리한다. 예시 수치나 프롬프트의 범용 기능을 승인된 게임 기능으로 추가하지 않는다.

## 설계와 제작

수석 개발·기술·게임 디자인·네트워크·운영 관점에서 목적, 비용, 경험, 성능, 유지보수를 검토한다. 핵심 재미를 먼저 검증하고 현재 규모에 맞게 설계한다.

복잡한 기능은 목적·규칙·상태·데이터·클라이언트/서버 책임·동기화·예외·검증을 정리한다. 단일 책임과 명시적 의존성을 유지하고 과도한 공통 관리자·싱글턴·무제한 RPC·상시 전체 동기화를 피한다.

게임 결과는 PlayFab의 운영자 전용 서버가 최종 결정한다. 폴더명과 대소문자를 임의 변경하지 않는다. 실제 파일이 생기면 담당 README의 구현 위치와 검사 방법을 갱신한다.

## 자료와 도구

사용자가 지정한 실제 자료를 확보·확인하고 출처·버전·권한·적용 위치를 남긴다. 유사물이나 임시 자원으로 임의 대체하지 않는다.

사용자가 제공한 Google 문서와 수록 사이트는 [개발 참고자료](REFERENCE_SOURCES.md)에 등록한다. 에셋·UI·음향·애니메이션·제작 도구 작업에서 관련 사이트를 우선 살펴보고, 실제 후보 링크와 선정 근거·기능 적합성·성능·라이선스를 기록한다. 원문의 설명은 현재 공식 조건과 프로젝트 결정에 대조하며, 후보 등록을 패키지 도입·구매·최종 디자인 승인으로 처리하지 않는다.

작업 시간을 줄이는 단축키·내장 기능·자동화를 안내한다. 유료 에셋·효과음·도구는 품질·시간·비용·호환성을 비교한다. 구매 의향은 결제·구독 승인과 구분한다.

## 검증과 운영

문서 작성, 코드 구현, 빌드, 로컬 플레이, 멀티플레이, 원격 CI, 배포를 증거에 따라 구분한다. 기존 완료 기록은 유지하고 새 검증을 연결한다.

작업에는 담당 폴더·실제 변경 파일·기대 결과·확인 방법을 기록한다. 버그, 유지보수, 운영, 검증 기록을 서로 연결한다. P0는 핵심 실행·기능 필수, P1은 출시 필수, P2는 출시 품질 향상, P3는 출시 이후 추가다.

Notion과 GitHub 게시 요청이 있으면 실제 저장 결과까지 확인한다. 기획 변경을 실행 환경 설치·서버 결제·게임 배포·실제 이용자 제재 승인으로 확대하지 않는다.
